# Discovery, onboarding and decisions

## First use

Identify the immediate objective. Apply a mode already chosen in the request or an applicable preference. Otherwise offer once: “Choose Professional or Presidential mode. You can switch later without changing project progress, approvals, or governance rules.” Continue permitted read-only discovery and use Professional while awaiting the choice. Silence is never authorization. No wizard is required.

Discover the context needed for this task through advertised tools and permitted inspection: applicable instructions, authoritative decisions, affected owners/contracts/consumers, test/build/operational conventions, and relevant existing records/capabilities. Inspect Git, trackers or other skills only when useful to the objective. Advertised does not establish authentication, functionality or permission. Reuse known current context and use targeted reading unless project instructions require more.

Do not automatically install, authenticate, modify config/docs, create records/branches/issues, run commands with side effects (including builds/tests/migrations), or probe production. Missing capabilities prompt supported fallbacks, not forced setup. Discover enough for the task; do not generate an exhaustive inventory.

Report briefly: mode, relevant conventions, available capabilities/limitations, blocking ambiguity, next permitted action. Reuse valid preferences on subsequent use and inspect changes. Persist preferences only in authorized storage. Optional roles/titles/language/formality need no upfront interview. Do not ask for country, political structure, credentials or model preferences.

## Requirements interview

Read existing accepted answers before asking. Ask only unresolved questions that can materially change scope, design, acceptance or authority; one significant question at a time, grouping related questions where useful. Offer a recommendation and reason, distinguish it from accepted requirements, and wait for business decisions that gate dependent work. Look up accessible environmental facts. Documented routine defaults may guide implementation; they cannot decide open business questions or contradict approvals.

For financial, historical or other derived effects, check the design-changing questions relevant to the actual path: authoritative source; correction/cancellation/restoration semantics; effects on later dependent movements; and original inputs, identity and versions that must be retained. Trace existing consumers before proposing answers. Reuse documented decisions; these prompts are not an obligatory interview for unrelated work. A newly discovered unresolved business policy pauses only dependent work and is surfaced as a decision, not silently chosen or expanded into implementation scope.

Preserve only conclusions/references, open/deferred questions and affected work, and next topic. If persistence is unauthorized, offer a compact conversational export under [records and authorization](records-and-authorization.md). Do not start a second authoritative requirements history.

## Knowledge ownership and documentation

Use the project's existing hierarchy, glossary, architecture documents and decision conventions. Code proves current implementation, not approved business requirements. Distinguish confirmed requirement, accepted decision, proposal, open question, deferred decision, implemented behavior, verified behavior, merged, deployed and operationally verified behavior.

When decisions change, retain history and exact supersession references. The governance record is an index, not a competing requirements document, decision log or completion history. Discover before creating. If necessary documents do not exist, propose the smallest useful set; obtain any required write permission. Do not impose GLOSSARY.md, ADR directories or new documentation just because a template or integration suggests them.

Before authoritative documentation edits identify exact files, reason, intended changes, confirmed requirements/decisions and supersession. Apply only covered changes; sufficiently specific existing permission remains valid. Unapproved required reconciliation blocks the affected completion boundary. Local notes and public-package docs still require their applicable authorized scope.

## Discovery integration

Read [integrations](integrations.md) before considering grill-with-docs or related skills. Inspection of a skill is not invocation. Never use another entrypoint to evade an invocation restriction. When unsupported or unable to respect documentation gates, use this original fallback: inspect relevant context, clarify terms, challenge assumptions with concrete cases, ask focused questions, separate decisions from proposals, then record only within authorized documentation scope. This fallback has no dependency on another skill.
